# Amazon 刈り取り / 価格差 自動検知システム（price-radar）

Amazon.co.jp で仕入れ・同市場で販売する運用向けに、値下がり検知・採算計算・承認・在庫出口・結果分析までを一気通貫で扱うシステムです。

- 技術構成: Next.js 16（App Router）/ Supabase（PostgreSQL）/ OpenRouter（AI）
- 画面: トップ（システム紹介）/ ダッシュボード / **8つの工程タブ**（①データ収集 → ⑧結果分析・改善）/ 商品詳細 / マイ商品（カート）/ 利用者管理（管理者のみ）/ 設定
- 左のタブは図解の8工程そのままで、工程ごとに項目（サブタブ）が並びます。URL は `/<工程>/<項目>`
- `/` はシステムの紹介ページ（ヘッダーのロゴから戻れます）。運用の入口は `/dashboard`
- 認証: メールアドレス＋パスワード（scrypt ハッシュ／httpOnly Cookie のセッション）。cron API は `CRON_SECRET` で保護
- 画面構成: 上にヘッダー（左ロゴ／右アバター）、左に工程タブ、その中にサブタブ

### 初期アカウント

| 権限 | メールアドレス | パスワード | できること |
|---|---|---|---|
| 管理者 | `admin@gmail.com` | `admin@gmail.com` | 利用者の**追加と削除のみ**（既存利用者の書き換えは不可） |
| 利用者 | `user@gmail.com` | `user@gmail.com` | 各機能の利用。アバターから利用者情報の変更と「マイ商品」へ |

初回アクセス時に、利用者が1人も居なければ自動で作られます。
**パスワードは初期値なので、運用に入る前に必ず変更してください**（アバター → 利用者情報の変更）。

新規登録（`/signup`）ではアバター・メールアドレス・名前・電話番号・パスワード・パスワード確認を入力します。
アバターはブラウザ側で正方形に切って 160px へ縮め、data URL として保存するので画像置き場の用意は不要です。

## 1. セットアップ

### 1-1. 環境変数

`.env.local` を用意します（`.env.example` を参照）。

| 変数 | 用途 | 必須 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase のプロジェクトURL | ✅ |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 公開鍵（現状は未使用） | ✅ |
| `SUPABASE_SECRET_KEY` | 秘密鍵。**サーバー側だけで使う** | ✅ |
| `CRON_SECRET` | 定期実行・ingest API を守る合言葉 | ✅ |
| `LINE_CHANNEL_ACCESS_TOKEN` / `LINE_TO_USER_ID` | LINE Messaging API 通知 | 任意 |
| `OPENROUTER_API_KEY` | AI分析 | 任意 |
| `KEEPA_API_KEY` | 価格収集（① データ収集）。**未設定だと価格を取得しません** | 任意 |

> LINE と OpenRouter は未設定でも動きます。通知は履歴だけ残り、AI分析画面は停止状態になります。

### 1-2. データベース

Supabase の SQL Editor で次の **1ファイルだけ** を全文貼り付けて実行します。

- `supabase/migrations/0001_init.sql`（スキーマの単一ソース。変更はこのファイルへ追記し、新規 SQL を作らない）

```bash
npm run db:verify   # テーブル・必須列の有無と行数を確認
npm run db:init     # settings に既定値を入れる
npm run db:seed     # デモデータ（商品・価格履歴・取引）
```

`db:verify` が「列が足りません」と出たら、`0001_init.sql` に列が追記されています。
同じファイルの全文をもう一度 SQL Editor で実行してください（`create ... if not exists` /
`add column if not exists` だけなので、再実行してもデータは消えません）。

### 1-3. 起動

```bash
npm install
npm run dev         # http://localhost:3000
```

ブラウザで開くとログイン画面が出ます。初期アカウント（上の表）で入ってください。

## 2. 使い方

| 操作 | 場所 |
|---|---|
| 値引きを探して候補を作る | ダッシュボード／候補の「スキャン実行」 |
| 購入を承認する（注文番号・実支払額は任意） | 候補カードの「購入する」 |
| 見送り理由を残す | 候補カードの見送り |
| 監視リストを確認する | 監視 |
| 在庫の売り時・撤退時を判定する | 在庫の「判定実行」 |
| 売却を記録する | 在庫 → 商品を選ぶ → 「売却を記録する」 |
| 条件を変える | 設定 |
| ビジネス割引の商品を探す | 割引検索 |
| 見つけた商品を手元に残す | 割引検索の一覧 →「カートに入れる」→ カート |

### ビジネス割引スキャン（割引検索）＝ 第一段階

「割引率の高い商品を見つける」ところまでを単体で完結させた機能です。
旧 backend（Python）/ frontend（Vite）の機能をこのアプリへ取り込んでいます。

1. 設定 → Amazonセッションで、ビジネスアカウントに手動ログインしてセッションを保存する
2. 割引検索でカテゴリ（1〜15）・割引率（5〜30%以上）・並べ替えを選ぶ
3. 「割引商品を検索する」を押すと、保存済みセッションで Amazon ビジネス割引ページを開き、
   絞り込み → スクロール取得 → 数量別価格から割引率を計算 → `discount_products` へ保存
4. 検索が終わると知らせのモーダルが出て、**割引率が高い上位5件を ChatWork / Slack / LINE すべてへ自動送信**
   （未設定の送信先は飛ばし、その旨を実行ログに残します）

実行ログは画面に出しっぱなしにせず、状況バーの「ログ表示」ボタンからモーダルで開きます。

取得のしかたで決めていること:

| 決めごと | 内容 |
|---|---|
| 割引率の求め方 | 数量別価格の各段で `(参考価格 − 単価) ÷ 参考価格`。**最も割引率の高い段**を採用（読めないときはバッジの表示値） |
| 保存する条件 | 指定した割引率**以上**のものだけ。Amazon側の絞り込みが効かなかった場合の取りこぼしをサーバー側でも止める |
| 保存の単位 | 3件たまるか1.5秒経つごとに保存。**見つかった順に画面へ出る**。途中で失敗しても取れた分は残る |
| 並べ替え | Amazon側は「ビジネス割引: 降順」を推奨（高割引から取れる）。画面側の表示順は既定で「割引率が高い順」 |
| 取り切る工夫 | 新着が止まってもページ末尾へ送って遅延読み込みを最大3回待ち、本当に終わりか確かめる |
| 中止 | 「実行を中止する」で停止。そこまでの結果は残り、状態は `canceled` になる |
| 落ちたときの復帰 | 10分間 `heartbeat_at` が更新されない実行は自動で失効。次のスキャンが始められなくなるのを防ぐ |
| 結果の見かた | 表の見出し（No／商品／数量／参考価格／ビジネス価格／割引率／割引額）を押すと、その列で昇順・降順に並べ替え。割引率でさらに絞り込み、CSV へ書き出し、過去のスキャンも履歴から再表示 |
| 選んだ商品 | 各行の「カートに入れる」で `cart_items` へ保存。スキャン結果（`discount_products`）は作業用リスト、カートが正式な保存先 |

スキャンは別プロセス（`scripts/amazon-discount-scan.ts`）で走り、進捗は `discount_scans.log`
に書かれて画面へ反映されます。手動で流すこともできます。

```bash
npm run amazon:login          # ビジネスアカウントへログインしてセッション保存
npm run amazon:scan -- <id>   # discount_scans の id を指定して実行
```

送信先の設定（未設定の先は自動で飛ばします）:
`CHATWORK_TOKEN` + `CHATWORK_ROOM_ID` / `SLACK_WEBHOOK_URL` /
`LINE_CHANNEL_ACCESS_TOKEN` + `LINE_TO_USER_ID`。
既定ではブラウザを表示して動きます（`AMAZON_SCAN_HEADLESS=1` で非表示）。

### 定期実行（本番）

```cron
*/5 * * * * curl -s -H "Authorization: Bearer $CRON_SECRET" https://example.com/api/cron/scan
0 * * * *   curl -s -H "Authorization: Bearer $CRON_SECRET" https://example.com/api/cron/notify
0 8 * * *   curl -s -H "Authorization: Bearer $CRON_SECRET" https://example.com/api/cron/exit-scan
0 */4 * * * curl -s -H "Authorization: Bearer $CRON_SECRET" https://example.com/api/cron/collect
```

### 価格の取り込み

```bash
curl -X POST https://example.com/api/ingest \
  -H "Authorization: Bearer $CRON_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"observations":[{"asin":"B0XXXXXXX","buyPrice":7000,"sellPrice":9900,"offerCount":6,"salesRank":1200}]}'
```

## 3. 8つの工程と画面

左のタブは図解の8工程で、各工程の中の項目がそのままサブタブになります。
古いURL（`/candidates` `/discounts` `/watch` `/positions` `/analytics` `/insights`）は移動先へ転送します。

| # | 工程 | URL | サブタブ（＝図解の項目） |
|---|---|---|---|
| ① | データ収集 | `/collect` | Amazon API / Keepa API / セラー情報 / その他データ |
| ② | 商品分析 | `/analysis` | 価格差の検出 / 利益の自動計算 / 売れ行き分析 / 競合分析 / リスクチェック |
| ③ | バックテスト・判定 | `/backtest` | 過去データで検証 / 価格変動の予測 / 購入条件の判定 |
| ④ | LINE通知 | `/notify` | 仕入れ候補をLINEで通知 / 送信履歴 / 通知の設定 |
| ⑤ | 購入承認・仕入れ | `/purchase` | あなたの承認で購入 / 購入数量の自動計算 / 購入履歴の記録 |
| ⑥ | 販売・在庫管理 | `/inventory` | 価格を継続監視 / 目標価格に達したら販売通知 / 販売価格の自動提案 / 在庫日数の管理 / 値下げ判断のサポート |
| ⑦ | 損切り・リスク管理 | `/risk` | 損切りラインの通知 / 長期在庫の売却判断 / 市場価格の急落を検知 / リスクの高い商品を事前に除外 |
| ⑧ | 結果分析・改善 | `/review` | 実績の自動集計 / 成功・失敗の要因分析 / ロジックの改善 / より精度の高い仕入れ判断へ |

### 各工程と実装の対応

| # | ステップ | 実装 |
|---|---|---|
| ① | データ収集 | `POST /api/ingest`（外部ワーカー）/ `GET /api/cron/collect`（Keepa）。**`KEEPA_API_KEY` 未設定のあいだ価格は取得されません**（動いているふりはしません）。割引検索の結果はカート追加時に `products` / `watch_universe` / `price_observations` へ取り込みます |
| ② | 商品の選定 | 出品ゲート（`UNKNOWN` は購入承認できない）＋ 手数料込みの純利益・ROI。割引率だけでは通しません |
| ③ | バックテスト | `/backtest/history`（画面）と `npm run backtest`（CLI）。`/backtest/forecast` は過去の傾向から先の価格を帯つきで出します。過去365日の観測をなぞり、勝率・平均利益率・平均保有日数・最大損失・PF を算出。**先読みをせず**、決着しなかった取引は勝率に混ぜません |
| ④ | 購入条件の自動算出 | 仕入上限価格 `maxBuyPrice` と推奨数量 `suggestedQty`（ケリー＋銘柄/カテゴリ上限＋現金留保） |
| ⑤ | LINE通知 → 承認 | `GET /api/cron/notify` で上位N件。承認は画面から。発注直前に価格・在庫・上限を再確認します |
| ⑥ | 購入後の監視 | `GET /api/cron/exit-scan` が日次で価格・競合・ランキング・保有日数・保管費を評価 |
| ⑦ | 再販売の判断 | 在庫詳細に「売却の提案」（**いくらで・何個**・急ぎ具合・段階値下げ）。売却フォームの初期値に反映されます |
| ⑧ | 実績の保存・改善 | 売却時に**失敗の原因**を記録。`/review/logic` で実績から**設定の見直しを提案**し、押したときだけ反映します（自動では変えません）。`/review/precision` は見込みと実績のズレを突き合わせます |

判断と提案はシステムが行い、**購入と売却の実行は人が承認します**。

### 処理の流れ（図・仕様対応）

1. **データ収集** — `POST /api/ingest` / 監視スキャン
2. **商品分析** — 手数料込の貢献利益・ROI・信頼度・仕入上限
3. **バックテスト的判定** — 30/90/180/365 日中央値・下落率・戦略パターン
4. **LINE通知** — Messaging API（未設定時は履歴のみ）
5. **購入承認** — `/purchase/approve` で承認／見送り（価格ドリフト・ゲート再確認）
6. **販売・在庫** — ポジション監視・目標価格
7. **損切り** — E-1..E-4 / X-1..X-4（45〜90 日の時間出口含む）
8. **結果分析** — 損益・勝率・Profit Factor → 閾値改善

**通知の門番**（すべて満たしたものだけ候補に出す）

1. 出品ゲート = PASS（FAIL/UNKNOWN は購入不可）
2. 純利益 ≥ 設定値 / ROI ≥ 設定値
3. 仕入価格 ≤ 仕入上限
4. 期待保有日数 ≤ 設定値 / 信頼度 κ ≥ 設定値
5. 1銘柄あたりの資金配分上限に収まる

## 4. 安全設計

| 項目 | 実装 |
|---|---|
| 秘密鍵の扱い | `SUPABASE_SECRET_KEY` はサーバー側のみ |
| RLS | 全テーブルで有効化しポリシーなし＝公開鍵からは拒否 |
| 定期実行API | `CRON_SECRET` の Bearer トークンが必要 |
| 発注直前の再確認 | 価格 3% 以上の変動・在庫切れ・仕入上限超過で中止 |
| 二重通知の防止 | 同一商品は24時間に1回まで |
| 全自動購入 | 既定で無効 |
